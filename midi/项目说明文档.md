# 管风琴 MIDI 上位机 —— 项目说明文档

> 版本：v0.1
> 范围：`D:\hadoop\midi\midi`（Qt 上位机源码）
> 内容：控制逻辑、通信逻辑、已实现功能、待完善/待添加功能

---

## 1. 项目概述

本项目是管风琴的 **MIDI 上位机**，运行于 Windows（Qt Widgets + QSerialPort，C++17）。
它把 MIDI 键盘的按键动作翻译为 48 路电磁阀的开关状态，并通过串口下发给 STM32 主控，
由主控经 CAN 总线分发到各从控板，最终驱动电磁阀。整条链路为：

```
MIDI 键盘 → 上位机(映射/编码) → STM32 主控 → CAN → 从控板 → PWM → 电磁阀
```

上位机本身不含音频，只负责「输入解析 → 状态维护 → 协议打包 → 串口收发 → 可视化」。

### 技术栈
- Qt Widgets（界面）、Qt SerialPort（串口）、WinMM `mmsystem`（MIDI 输入）
- 构建：qmake（`midi.pro`），C++17
- 平台：Windows（`win32:LIBS += -lwinmm`）

## 3. 控制逻辑

### 3.1 输入：MIDI → 状态表

1. **驱动回调（非 GUI 线程）**：`MidiInput::midiCallback`（`midiinput.cpp:90`）。
   WinMM 将短消息压入一个 DWORD：`status=低8位`、`data1=次8位`、`data2=高8位`，
   `parameter2` 为毫秒时间戳。
2. **跨线程安全投递**：回调内不做业务，仅用
   `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 把数据投回 Qt GUI 线程
   （`midiinput.cpp:118`），并先用 `isOpen()` 过滤关闭后残留的消息。
3. **字节翻译**：`parseMessage`（`midiinput.cpp:130`）按 `status & 0xF0` 分类：
   - `0x90` NoteOn（**力度为 0 视为 NoteOff**，MIDI 惯例）
   - `0x80` NoteOff
   - `0xB0` ControlChange
   - 其它 → Other
4. **双监听**：`midiEvent` 同时被两处接收：
   - `MainWindow::onMidiEvent`（`mainwindow.cpp:254`）：仅显示、计数、格式化日志。
   - `AppController::handleMidiEvent`（`appcontroller.cpp:70`）：真正的业务处理。

### 3.2 映射规则

- `阀号 valveIndex = 音符 note − baseNote`，`baseNote` 默认 **36**（C2）。
- 有效范围 `0 ~ 47`，超出忽略（`notemapper.cpp:12`）。
- 于是音符 **36→阀0**，音符 **83→阀47**。
- 反推：`boardId = valveIndex / 16`（0~2），`channel = valveIndex % 16`（0~15）。

### 3.3 状态维护：全量而非增量

`OrganState` 用 `std::bitset<48>` 保存整张状态表（`organstate.h`）。
每次按键/松键都修改这张表，再由 `pushState()`（`appcontroller.cpp:115`）**整体下发**。
采用全量状态的目的是：幂等、抗丢帧、避免状态漂移。

### 3.4 输出：状态 → 界面 + 串口

`pushState()` 做两件事：
1. `emit valveStateChanged(bitmap)` → `ValvePanel::setState` 重绘方格；
2. 若串口已打开，`SerialLink::send(Command::SetState, bitmap)` 下发 6 字节位图。

### 3.5 安全兜底

串口断开时 `SerialLink` 发 `connectionChanged(false)`，
`AppController` 立即调用 `allOff()`（`appcontroller.cpp:22-27`）把全部阀置关。
此时串口已断，`pushState()` 只刷新界面、不发帧。

### 3.6 线程模型

全项目只有 **一处线程边界**：WinMM 回调线程。回调用队列连接把数据交回 GUI 线程，
其余所有逻辑（状态维护、串口收发、绘图）均在 GUI 线程内串行执行，无并发竞争。

## 4. 通信逻辑

### 4.1 帧格式

```
+------+------+------+-------------+-------+------+
| SOF  | LEN  | CMD  |  PAYLOAD    | CRC8  | EOF  |
| 0xAA | 长度 | 命令 |   数据...   | 校验  | 0x55 |
+------+------+------+-------------+-------+------+
```

- `LEN` 为单字节，即 payload 最大 255 字节。
- **CRC8**：多项式 `0x07`、初值 `0x00`，覆盖 `LEN + CMD + PAYLOAD`
  （`frame.cpp:3`、`frame.cpp:32`）。
- 打包：`Frame::encode`（`frame.cpp:21`）；解析：`Frame::decode`（`frame.cpp:39`）。

### 4.2 命令字（`command.h`）

| 值 | 命令 | 方向 | 载荷 |
|---|---|---|---|
| 0x01 | `SetState` | 上位机→主控 | 6 字节位图（48 路全量） |
| 0x02 | `SetOne` | 上位机→主控 | boardId, channel, state |
| 0x03 | `AllOff` | 上位机→主控 | 无 |
| 0x10 | `Ping` | 上位机→主控 | 无 |
| 0x11 | `Pong` | 主控→上位机 | 无 |
| 0x12 | `GetStatus` | 上位机→主控 | 无 |
| 0x13 | `Status` | 主控→上位机 | boardId, errCode |

> **实际发送情况**：上位机目前只发出 `Ping`（连接后验证链路，`mainwindow.cpp:244`）
> 和 `SetState`（每次状态变化）。`SetOne` / `AllOff` / `GetStatus` 虽已定义但**从未发送**；
> `allOff()` 实际发送的是一帧全 0 的 `SetState`。

### 4.3 位图语义

`OrganState::snapshot()`（`organstate.cpp:29`）导出 6 字节：

```
字节索引 = valveIndex / 8
位索引   = valveIndex % 8   （LSB 对齐）
```

| 字节 | 覆盖范围 | 位序 |
|---|---|---|
| byte0 | 板0 通道0–7 | bit0=ch0 … bit7=ch7 |
| byte1 | 板0 通道8–15 | bit0=ch8 … bit7=ch15 |
| byte2 | 板1 通道0–7 | 同上 |
| byte3 | 板1 通道8–15 | 同上 |
| byte4 | 板2 通道0–7 | 同上 |
| byte5 | 板2 通道8–15 | 同上 |

例：仅阀 0 开 → `byte0=0x01`；仅阀 47 开 → `byte5=0x80`。

### 4.4 接收与切帧

`QSerialPort::readyRead` → `handleReadyRead`（`seriallink.cpp:158`）：
1. 新数据追加到 `m_rxBuffer`（一帧可能分批到达）；
2. 跳过开头非 `0xAA` 的脏字节；
3. 长度不足则等待下次；
4. 凑满 `LEN+5` 字节后交 `Frame::decode` 校验；
5. 校验通过 `emit frameReceived(cmd, payload)`，再移除该帧；
6. `AppController::handleFrameReceived`（`appcontroller.cpp:98`）分发：
   `Pong`→记录"主控在线"，`Status`→打印十六进制，其它→记录命令字。

### 4.5 串口参数

真实模式打开串口参数为 **115200 / 8 数据位 / 无校验 / 1 停止位 / 无流控**
（`seriallink.cpp:57-63`），下位机侧必须一致。

### 4.6 模拟模式

`SerialLink` 内置"假主控"（`seriallink.cpp:119`）：开启后不占用真实串口，
`isOpen()` 返回 `m_simulatedOpen`，`send()` 转去 `handleSimulatedFrame`，按命令自答：

- `Ping → Pong`
- `SetState` / `SetOne` → 打印位图
- `AllOff` → 打印全部关闭
- `GetStatus → Status{0x00, 0x00}`

使"连接→发帧→收帧→解析→刷界面"整条链路在无硬件时也能验证。

### 6.2 下位机（需另建固件工程，仓库中暂无）

仓库内没有 STM32 固件，需新建两层程序：

**A. 主控板固件**
1. PC 链路：USB CDC 虚拟串口，115200/8N1（须与上位机一致）
2. 帧接收状态机（移植 `frame.cpp` 逻辑）+ 环形缓冲/DMA，处理粘包与分帧
3. CRC8（0x07/初值 0）与上位机逐字节一致
4. 命令分发：`Ping→Pong`、`SetState` 拆分 3 组 16 位、`SetOne`/`AllOff`/`GetStatus`
5. 帧发送编码（回包同格式）
6. CAN 主机：下发通道状态、接收从控状态/错误
7. 心跳/看门狗：超时无有效数据 → 广播全关（fail-safe）
8. 状态指示（LED/蜂鸣，可选）

**B. 从控板固件（×3，同一份固件靠 boardId 区分）**
1. CAN 接收，验收滤波器只收本板 ID
2. 16 路位图/单路命令解析
3. 电磁阀驱动（GPIO 或 TIM PWM）；建议"吸合-保持"策略（全压吸合 N ms → PWM 保持）
4. 电流采样 / 过流保护 → errCode（可选）
5. 状态回传 `{boardId, errCode}` → 主控 → 上位机 `Status`
6. 失联看门狗：CAN 超时无命令 → 本板全关

**C. 尚需约定的接口规范（代码中不存在）**
- CAN 协议：建议 11 位 ID，如 `0x100|boardId` 发整板 16 位位图（DLC 2）、
  `0x110|boardId` 单路、`0x1FF` 广播全关、`0x2xx` 从控→主控状态；速率 250/500 kbps
- 两端共享的协议头（命令字、CRC、帧格式）应统一维护

## 7. 附：关于 `mainwindow.ui`

`mainwindow.ui` 是 Qt Designer 模板遗留文件，当前**不参与构建**（`.pro` 无 `FORMS`），
界面完全由手写代码 `buildUi()`（`mainwindow.cpp:56`）生成。
改用 `.ui` 的影响：
- 需在 `.pro` 增加 `FORMS`，由 `uic` 生成 `ui_mainwindow.h`；
- `mainwindow.h/.cpp` 的成员指针改为 `ui->控件名`，并删除 `buildUi()`；
- 自定义控件 `ValvePanel` 必须在 Designer 中"提升（Promote）"；
- 信号连接需在构造函数中重做或使用自动连接命名约定；
- 功能与性能无实质变化，`ValvePanel` 绘制逻辑不受影响。
